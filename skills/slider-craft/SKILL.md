# スライド作成

日本語の報告・提案スライドを作る、直す、検査する。

**このスキルの価値は「pptx を出力すること」ではなく「読んだ相手が判断できる資料にすること」にある。**
きれいだが何が言いたいか分からない資料は、無いのと同じ。

**そのために、作る側だけでなく、受け取る側の目でも読む。**
作り手は自分の資料を読めない。書いていないことを頭で補ってしまうため。
手順2と手順5で `references/80_audience.md` に従い、**先方になりきって疑問を出す。**
常に「今どの段階にいて、次に何を確定するか」を示す。

### 役割 — 誰として、何を優先するか

**手順に書いていない場面は必ず出る。そこで何を取るかがこれ。**

| | |
|---|---|
| 誰として | 資料を作る側の担当者として。**読むときだけ先方の目に切り替える** |
| 最優先 | **先方が判断できること。** 見た目の完成度でも、枚数でも、作業の早さでもない |
| **誰の側に立つか** | **利用者が資料で達成したい結果の側。利用者の手間や気分の側ではない** |
| しないこと | 数値を推測で埋めない。テンプレートの体裁を勝手に変えない。資料を外に出さない |

**「誰の側に立つか」が、指摘を弱めるかどうかを決める。**
利用者は作り手なので、厳しい指摘は歓迎されないことがある。
**それでも弱めない。** 弱めた指摘は本番で先方から出て、そのときは直せない。
**褒めない。** 穴を見つけるのが目的（`references/80_audience.md`）。

## 資料を外に出さない ★最初に読む

**扱うのは、まだ外に出ていない資料。** 提案前の提案書、社外秘の報告書、
利用者の組織のテンプレート。**一度外に出ると取り消せない。**

### 公開しない

**禁じるのは「他人が見られる状態にすること」。** 非公開のまま扱うことは禁じない。

| してはいけない | 何が起きるか |
|---|---|
| **公開する・リンクを共有する** | 誰でも開ける。**取り消せない** |
| **第三者が開ける状態にする**（共有設定、共有ドライブ、gist、pastebin） | 同上 |
| オンライン変換サービスに上げる | 中身を保持することがある |
| **資料やテンプレートを git に入れる** | private でも、組織の外に出たことになりうる。テンプレートは `.gitignore` で除外する |
| 本文や図表を外部サービスに送る | 数値・宛先がそのまま渡る |

**自分の判断では一切やらない。** 「共有リンクを出しましょうか」と**提案もしない。**
提案は実行への一歩で、断る手間を利用者に負わせる。

### 非公開のまま使うのはよい

| 手段 | 可否 |
|---|---|
| **Browser ペインに `file://` で開く** | **よい。**機械の外に出ない。**既定はこれ** |
| **利用者だけが開ける Artifact** | **よい。**ただし中身は claude.ai 上に載る（手元だけの状態ではなくなる） |
| ローカルに PNG / pptx を書く | **よい** |
| `SendUserFile` で利用者本人に渡す | **よい** |

**既存の非公開 Artifact を消す必要はない。** 消すかどうかは利用者が決める。
**こちらから削除を促さない。**

### 出してよいもの

| 手段 | 可否 |
|---|---|
| ローカルのファイルに書き出す（`deck/`、`work/`、`qa/`） | **よい。**これが既定 |
| 会話の中に文言・構成を書く | よい |

**「利用者に見せる」と「外部に載せる」を混同しない。**
前者はこの仕事そのもので、後者は禁止。

## 進め方

```
作業の進捗:
- [ ] 0. 前提の確認（作業ディレクトリ・テンプレート・道具）
- [ ] 1. 意図の確定（背景・目的・相手・フェーズ）★止まる
- [ ] 2. 骨子の設計（ストーリーライン）＋ 先方の目で通し読み ★止まる
- [ ] 3. 1枚ずつ中身を決める（メッセージ＋図解の型）
- [ ] 4. HTML を作る／直す
- [ ] 5. 検査（HTML の絵・文章・先方の目）
- [ ] 6. 絵を見せて、指摘を HTML に反映する
- [ ] 7. （pptx が要るとき）変換と pptx の検査 → slider-deck に委譲
- [ ] 8. （依頼があれば）別テンプレートへの載せ替え → slider-reskin に委譲
```

このチェックリストを回答に写し、進むたびに埋める。

### 0. 前提の確認

**作業ディレクトリを最初に確認する。** リポジトリの外で作業すると、成果物が
どこに残ったか分からなくなる。

| 確認すること | 無いときの動き |
|---|---|
| 出力先ディレクトリ | 利用者に確認せず `deck/` を作り、理由を1行述べる |
| 資料テンプレート（リポジトリ直下 `assets/templates/deck/`） | **あればそれに従う。**無ければ既定の配色規約で作る。**勝手にテンプレートを探しに行かない**。テンプレートには2つの形があり、**扱いが違う**（下表） |
| `python-pptx` / `openpyxl` | `python3 -m pip install python-pptx openpyxl` |
| 画像化の手段 | `python3 <slider-deck>/scripts/qa_render.py --probe` で確認する。**Windows は PowerPoint COM に自動で切り替わる。**どちらも無ければ手順5で目視を依頼し、**検査していないと明記する** |
| テンプレートの形式とサイズ | HTML 一式なら `template-manifest.md`、.pptx なら `fit_check.py budget --template <t>.pptx`。**16:9 に決め打ちしない** |

#### まずテンプレートを選ばせる ★ここで止まる

**テンプレートは複数ある。勝手に決めない。**
同じデザインでも比率が違えば1枚に入る文字数が変わり、骨子ごと変わる。

```bash
ls -d assets/templates/deck/*/
```

見つかったものを一覧で出し、**どれを使うか聞く。**
各テンプレートの `template-manifest.md` 冒頭 `slide_size` から比率と用途を読んで添える。

| テンプレート | スライドサイズ | 向き | 使いどころ |
|---|---|---|---|
| `<横長のテンプレ>` | 960×540pt（16:9） | 横長 | 投影して話す。画面で読む |
| `<紙向けのテンプレ>` | 780×540pt（13:9） | A4 に近い | **印刷して配る。紙で読む** |

**名前は利用者が置いたものに従う。** ここに書いた名前は例。

**1つしか無ければ聞かずにそれを使い、理由を1行述べる。**
利用者が「A4で」「投影用で」と述べていれば、それで確定させて聞かない。

#### テンプレートの形を先に見分ける

**見分けを飛ばすと、HTML テンプレートがあるのに .pptx を探し始めて止まる。**

| 見分け方 | 形 | 手順4での起こし方 |
|---|---|---|
| ディレクトリに `template-manifest.md` がある | **HTML 一式**（px 絶対座標） | **種別ごとの HTML をコピーして文字だけ差し替える。**`make_html.py` は使わない |
| `.pptx` が1個ある | pptx テンプレート | `read_template_style.py` で書体・配色を読み、`make_html.py --template` で起こす |
| どちらも無い | 無し | 既定の配色規約。`scripts/gen_deck_templates.py` で汎用テンプレートを作る |

**HTML 一式の方が優先。** 両方あるときは HTML を採る。
同梱の `.pptx` は HTML から出した確認用の派生物であり、テンプレートの正本ではない
（`preview/` に置く）。

### 1. 意図の確定 ★ここで止まる

`references/10_intent.md` を読む。**4点が埋まるまで骨子を書き始めない。**

| 問い | 確定させること |
|---|---|
| 何のプロジェクトで、何が問題か | 背景と課題。**現状と、あるべき姿の差** |
| 誰に、何を判断してほしいか | 相手と、相手に取ってほしい行動 |
| どのフェーズの資料か | 提案／中間報告／最終報告／意思決定依頼 |
| この資料の成功とは何か | 資料を見た相手が何をしたら成功か |
| **各スライドの役割** | その枚で**先方に何を伝えるか**。手順2の骨子の列になる |

**会話の中に既に材料があることが多い。** まず会話履歴とファイルから拾い、
足りない分だけ聞く。全部を質問しない。

### 2. 骨子の設計 ★ここで止まる

`references/20_story.md` を読む。**スライドは1枚も作らない。**
出すのは、スライド番号・見出し・**役割**・メッセージライン・図解の型 の一覧表だけ。
**メッセージラインは、その枚の役割に答える形で書く。**役割に答えていない ML は、
その枚が要らないか、役割の書き方が曖昧かのどちらか。

**同時に用語台帳を作る**（`references/47_terms.md`）。同じものを指す語を1つに決め、
数値台帳（`46_numbers.md`）と並べて持つ。**初めての領域ほど語が揺れる。最初に作る。**

そのうえで `references/80_audience.md` を読み、**先方になりきってメッセージラインを
通し読みする。** 手順1で確定した相手の立場・姿勢・決裁権から役を作る。
**ここで構成の穴を潰すのが最も安い。**作り込んでから出ると作り直しになる。

**一覧表と、先方の目で読んだ結果を一緒に出して承認をもらう。**
骨子が違うまま中身を作ると、全部作り直しになる。

### 3. 1枚ずつ中身を決める

`references/30_visual.md` と `references/40_japanese.md` を読む。

1枚につき次を決める。**箇条書きを既定にしない。**

- メッセージライン（そのスライドで一番言いたいこと、言い切り、1文）
- 図解の型（`assets/templates/INDEX.md` から選ぶ）
- 図に入れる具体的な値と項目
- 話す内容（スライドではなくスピーカーノートに置く）

**図解の型が選べないスライドは、そのスライド自体が不要な可能性が高い。**
消せないか先に検討する。

**文言を書く前に `references/45_layout.md` を読み、入る量を先に決める。**
書いてから縮めるのではなく、上限を見てから文言を決める。往復の大半はここで消える。

```bash
python3 <slider-deck>/scripts/fit_check.py budget --template <テンプレ>.pptx --box <幅>x<高さ> --pt 16
```

### 4. HTML を作る／直す

**成果物は HTML 一式。ここで pptx は作らない**（手順7で `slider-deck` に渡す）。

**「元の .pptx を出せ」と要求しない。** HTML から始まる仕事では存在しない。
要るのは**テンプレート**であって、元の pptx ではない。

**大きく組み直すときは、論点の中心になる数枚（3〜4枚）を先に作って見せる。**
全体を作ってから方向違いが分かると、全枚が手戻りになる。実績では、先に4枚を
見せてから広げたほうが往復が少なかった。**中心の数枚で合意してから残りに広げる。**

**初めて作るときの土台は、テンプレートの HTML。**白紙から書かない。
手順0で見分けた形で分岐する。

```bash
# A. HTML 一式のテンプレート（template-manifest.md がある）← まずこれを探す
#    手順0で選んだテンプレートから、種別ごとの HTML をコピーし、
#    **座標・サイズ・書体は変えずに文字だけ差し替える**
cp assets/templates/deck/<選んだテンプレ>/003.html work/p01.html

# B. pptx テンプレート
python3 scripts/make_html.py --template <テンプレ>.pptx --outline outline.md -o work/deck.html
```

**ファイル名はテンプレートのものを引き継ぐ**（`003.html` → `p03.html` ではなく
`003.html` のまま使えるなら、そのまま）。
名前が残っていると、別テンプレへの載せ替えで割付が確実に決まる
（`slider-reskin/references/10_rules.md`）。

**A で座標や文字サイズを動かさない。**テンプレートの実測値であり、
動かすと元の資料と並べたときに合わなくなる。入らないなら
[文言を減らすか、スライドを分ける](references/45_layout.md)。

### 5. 検査 ★止まらないが、必ず行う

**見るのは HTML の絵。** pptx の検査は `slider-deck` の仕事。

```bash
python3 scripts/html_png.py work/*.html -o qa_html
```

**往復は2つの段階に分かれる**（`48_html.md`）。段階で見るものが変わる。

| 段階 | 詰めるもの | 見るもの |
|---|---|---|
| 0 | テンプレート自体のずれ | 1枚だけ pptx にする |
| 1 | テキストと大枠のレイアウト | **HTML の絵** |
| 2 | 見た目・装飾・レイアウト | **pptx**（提出先の環境） |

**段階の切り替えは利用者が宣言する。** 自分で決めない。
**宣言があるまでその段階を回し続ける。**「そろそろ次では」と促さない。
回数でも、指摘が減ったことでも打ち切らない。

**段階2から段階1へ戻ってよい。** 利用者が宣言したら戻る。
ただし**戻ると段階2で詰めたものが崩れる**ので、
何が崩れるかを一覧で出してから戻る（`48_html.md`）。

**段階2で提出先の環境を再現できないなら、そう言う。**
和文フォントが違えば折り返し位置が変わり、**実装では埋まらない。**
**指摘には画面の画像を添えてもらう。**

**相手もこのスキルを使うなら、環境差は相手側で解ける。**
解けないのは受け渡し（正本の所在・進捗・テンプレートの同梱）。
担当が分かれるときは `references/49_handoff.md` を読む。

**段階2（pptx）に入ったら `slider-deck` に渡す**（手順7）。
**pptx の絵と HTML の絵を並べるのは向こうの手順3。**

**画像を1枚ずつ自分で見る。**抜き取りでは見落とす。
利用者に「確認してください」と丸投げしない。

**各ツールが出す `検査: ... 対象 n... 指摘 n件 前提: ...` の行を、報告にそのまま貼る。**
**出力の末尾だけを読まない。**不合格の一覧は途中にある。
実際にそれで「ゼロ」と誤報告した。

**続けて `references/80_audience.md` に従い、先方の目で全スライドを読む。**
見た目と文章が通っていても、**先方が判断できない資料は不合格。**

#### 検査の関所 ★必須。下の欄を全部埋めるまで「できました」と言わない

**規則を参照ファイルに書くだけでは守られなかった。**実績：前の版の対比、
作り手の作法、1行の ML、カンペの飛びが、規則を足した後の版でも残った。
**機械で見られるものは機械で見て、残りは報告の欄で必ず答える。**

```bash
python3 scripts/ledger_check.py work/*.html --terms terms.md --numbers numbers.md --history --ml
```

**報告に必ず入れる表。空欄を残さない。「該当なし」も書く。**

| 項目 | 書くこと |
|---|---|
| 機械検査 | `ledger_check` の `検査:` 行をそのまま。**古い語・古い値・ML の型は 0 件になるまで直す** |
| 前の版を知らない聞き手で読んだ | 経緯の印（〜ではなく・まだ・ここでは・前回）の**各件をどう処理したか** |
| 作り手の作法が出ていないか | 見た枚数と、落とした文（「率で比べる」の類） |
| 表の中の記号 | 意味を持つ記号が残っていないか（「ー」「○」） |
| 目次・全体像・ページ番号 | 構成を変えたなら照合したか。**目次は1項目1行か** |
| 目標・段の図 | 現状を起点として描いたか |
| カンペ | **あるなら**、計算の飛び・定義前の用語・枚の断絶の検査結果。無ければ「無し」 |
| 見せ方 | **HTML を非公開 Artifact で見せたか**（PNG を見せていないか） |

検査で不合格なら手順6へ。**合格するまで「できました」と言わない。**

### 6. 絵を見せて、指摘を HTML に反映する

**同じ指摘が2回来たら、その枚だけでなく全枚を照合する**（`<slider-deck>/references/55_revise.md` 3-4）。
**本文の差し替えは `splice.py`、直した後は `ledger_check.py`**（`48_html.md` 3-3）。

**利用者に見せるのは HTML。** 見せ方の既定は**利用者だけが開ける Artifact**。
**利用者のUI操作が要る手段を既定にしない**（Browser ペインは、こちらから前面化できない）。
**PNG を見せない**（`48_html.md`）。見せ方の順はそこに書いてある。

**見た目の指示を受けたら、直す前に絵を出す。**
利用者は絵を見て指示するが、こちらは HTML の文字列しか見ていない。
**同じものを見ていないので、「ここ」「大きい」「寄っている」は HTML からは分からない。**

```bash
python3 scripts/html_png.py work/*.html -o qa_html   # 利用者が見たのと同じ絵
```

絵を見て、**どこを指しているかと、直した後どうなるかを述べてから直す。**
特定できなければ、絵を見せて「これですか」と聞く。**推測で直さない**（`48_html.md`）。

**利用者が手で編集したファイルを受け取ったら、二度と再生成しない。**
以後は該当スライドだけ直す。**利用者のファイルを上書きせず、別名で保存する。**

**出力された pptx を手で直さない。**再生成で消えるうえ、同じ不具合が次回も出る。

直したら、**どのスライドの何を変えたかを言葉で出す。**

### 7. pptx への変換と検査（pptx が要るとき）

**`slider-deck` スキルに委譲する。** ここでは行わない。

「パワポにして」「提出用のファイルを作って」と言われたら、そのスキルに渡す。
変換・段階0・溢れの検査・pptx の画像化・差分の抽出まで、向こうが持っている。
**本スキルで再実装しない。**

**渡すのは HTML 一式とテンプレート。**
向こうで見つかったずれは **HTML に差し戻って**くるので、手順6に戻る。

### 8. 別テンプレートへの載せ替え（依頼があったときだけ）

**`slider-reskin` スキルに委譲する。** ここでは行わない。

「この資料を別のテンプレートに直して」と言われたら、そのスキルに渡す。
テンプレートの一覧提示・レイアウトの割付・欠落の検出まで、向こうが持っている。
**本スキルで再実装しない。**

**渡すのは HTML 一式。pptx ではない。**
向こうも HTML を載せ替える。**pptx を渡すと、正本でないものを直すことになる。**

## 承認ポイント — どこで止まるか

| 止める | 止めない |
|---|---|
| 手順1の意図（背景・目的・相手・フェーズ） | 図解の型の選定 |
| **どのテンプレートを使うか**（複数あるとき） | 配色・フォント・レイアウトの調整 |
| 手順2の骨子（スライド一覧） | 種別ごとの HTML の選択 |
| **段階の切り替え**（利用者の宣言。進むのも戻るのも） | 段階の中の直し |
| **pptx を提出先・第三者に渡す操作** | 手元での変換と検査 |
| **資料テンプレートを書き換える操作** | 案件ディレクトリの中の直し |
| 既存の pptx を上書きする書き込み | 新規ファイルの生成 |
| 資料を外部に送る操作（**公開は禁止。**上記「資料を外に出さない」） | 手順5〜6の手直しの往復 |

**上記以外は聞かずに進める。** 判断したら理由を1行述べる。承認は待たない。

**止まるときは、その時点で未決のものを全部まとめて出す。**
承認1件につき1ターンを使わない。

## 自律判断の基準

### 聞かずに決める

- 図解の型の選定（`30_visual.md` の対応表で決まる）
- スライドの枚数（フェーズごとの目安が `20_story.md` にある）
- 配色・フォント・文字サイズ・余白（テンプレートがあればそれに従い、無ければ既定値）
- ファイル名と出力先
- どちらの経路にするか（HTML を受け取ったら HTML 経路、素案だけなら利用者に合わせる）
- 手順5で見つけた不具合の修正（重なり・はみ出し・溢れはゼロまで直す）

**指摘を弱めるかどうかは冒頭の「役割」が決める。** ここでは繰り返さない。

### 必ず確認する

1. 数値の出所が分からないとき。**推測値でグラフを作らない**
2. 相手に取ってほしい行動が2つ以上あるとき。どれが主かで構成が変わる
3. テンプレートのレイアウトに収まらない量の内容があるとき。**削るか分けるかは利用者の判断**
4. 利用者が編集したファイルを受け取ったとき。**上書きしてよいかを必ず聞く**

### 聞き方の型

**確認を求めるとき、渡すべき情報が落ちる形で失敗する。** 型で防ぐ。

値を確かめるとき（数値の出所、枚数、サイズ）は、
**その値が何に使われ、間違えるとどうなるか**を添える。
「この数字で合っていますか」だけでは、利用者は判断できない。

選んでもらうとき（どれを削るか、どちらの構成か）は、
**全案に メリット・デメリット・コスト を揃え、推奨に理由を1行付ける。**
デメリットの無い案が1つでもあれば、利用者はそれを選ぶしかなくなる。
**「何もしない（現状のまま出す）」を必ず1案に入れる。**

**見た目や構成の選択肢は、文章で比べない。両案を絵にして並べる。**
チェックシートの形や散布図の見せ方のように、見た目で決まるものは
言葉で説明しても伝わらない（実績：説明したが伝わらず「両方見せて」と言われた）。
**各案を HTML で作り、並べて見せてから選んでもらう。**

### 指示の読みが2通りあるとき

**直す前に、自分の読みを1行で書く。**それから直す。
「〜としないで」「〜くらいに」のような指示は、読み方で結果が逆になる。
先に読みを書くと、外れていれば利用者がすぐ気づく（実績：これで早めに外れが分かった）。
**聞いて止まるのではない。**読みを書いて、そのまま進める。
